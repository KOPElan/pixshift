# PixShift 实施计划

## 1. 计划基线

- 范围：完成产品需求文档定义的 macOS MVP。
- 人力假设：1 名全职 macOS 开发者。
- 预计开发量：30 个有效开发日，另留 5 日风险缓冲。
- 计划周期：6 个开发周 + 1 个缓冲周。
- 开发方式：小步纵向交付，每周末均应得到可运行、可测试的构建。
- 发布目标：先交付签名的自用版本，保留 Mac App Store 上架条件。

工期是当前需求基线下的工程估算，不包含品牌设计、商店审核等待、额外格式、远程统计或需求变更。

## 2. 执行顺序

```text
技术风险验证
  ├── WebP 编码与签名
  ├── App Sandbox 原目录写入
  └── 元数据/GPS 清理
          ↓
工程基线 → 导入队列 → 原生格式处理 → 统一裁剪
                                     ↓
        设置与输出规则 ← WebP 编码 ←┘
                 ↓
        并发、进度、取消与清理
                 ↓
       本地化、性能、签名与发布验证
```

关键路径是“风险验证 → 处理引擎 → 输出与沙盒 → 任务台账与取消 → 发布验证”。UI 细节不能阻塞处理引擎和文件安全测试。

## 3. 开工前技术验证（2 日）

这些验证必须最先完成，以免在开发后期推翻架构。

### SPIKE-01：WebP 编码链路

- 将官方 `libwebp` 构建为 arm64 与 x86_64 可用的静态库或 XCFramework。
- 从 Swift 调用最小 C wrapper，将 RGBA 测试缓冲编码为 WebP。
- 验证品质参数、透明通道、最大尺寸错误和内存释放。
- 验证 Debug/Release、签名与 Archive 不包含 `cwebp` 可执行文件。
- 记录固定版本、构建命令、许可证和升级方法。

通过标准：生成的 WebP 可被至少两个独立读取器打开，Archive 构建通过。

### SPIKE-02：沙盒文件权限

- 创建启用 App Sandbox 的最小应用。
- 验证文件选择、文件夹选择和拖放三种导入方式。
- 验证单文件授权是否允许在父目录创建同级输出。
- 验证统一输出目录的 security-scoped bookmark 在重启后恢复。
- 明确权限不足时的二次文件夹授权流程。

通过标准：形成一份可重复的权限测试表，默认原目录导出不存在静默失败路径。

### SPIKE-03：元数据往返

- 准备带 EXIF、GPS、ICC 与方向字段的 JPEG、HEIC、TIFF、WebP 样本。
- 验证方向归一化、GPS 清除和 ICC 保留策略。
- 验证 WebP mux 写入允许元数据的方式。

通过标准：自动检查确认输出不包含 GPS，视觉方向正确，色彩配置符合设计。

## 4. 六周开发排期

### 第 1 周：工程基线与导入队列

目标：得到可运行的原生窗口，三种导入入口形成统一队列。

任务：

- ENG-001：创建 SwiftUI macOS 工程、测试 targets 和目录结构。
- ENG-002：配置 macOS 15、Swift 6 严格并发、沙盒 entitlement 和 String Catalog。
- ENG-003：定义 `ImageJob`、输入格式、队列状态和结构化错误模型。
- ENG-004：实现文件选择器、文件夹选择器和拖放入口。
- ENG-005：实现非递归目录扫描、隐藏项过滤、格式校验和 URL 去重。
- ENG-006：实现异步缩略图、图片尺寸与格式读取。
- UI-001：实现主窗口空状态、队列表格、移除和清空操作。
- TEST-001：覆盖目录扫描、去重、格式识别和错误映射单元测试。

周验收：JPEG、PNG、WebP、HEIC、TIFF 可通过三种入口加入同一个队列；UI 不因大目录扫描阻塞。

### 第 2 周：尺寸算法与原生格式流水线

目标：完成 JPEG、PNG、HEIC、TIFF 的端到端尺寸处理与新文件导出。

任务：

- ENG-007：实现六种 `ResizeMode` 的纯函数计算。
- ENG-008：实现禁止/允许放大和整数像素舍入规则。
- ENG-009：实现 EXIF orientation 归一化。
- ENG-010：实现 Core Image/Core Graphics 裁剪、缩放和 alpha 背景合成。
- ENG-011：实现 Image I/O 原生编码器和格式能力探测。
- ENG-012：实现 JPEG/HEIC 品质、PNG/TIFF 无损输出。
- ENG-013：实现兼容元数据保留、GPS 移除和 ICC 处理。
- UI-002：实现尺寸模式、数值验证、“允许放大”和格式/品质控件。
- TEST-002：建立尺寸矩阵、方向、透明背景和原生格式集成测试。

周验收：四种原生格式可批量导出，exact 模式不拉伸，原文件哈希和修改时间不变。

### 第 3 周：统一裁剪编辑器

目标：完成 Photoshop 风格裁剪交互，并将同一相对区域安全应用到整个批次。

任务：

- ENG-014：实现归一化裁剪几何、比例约束和越界平移算法。
- UI-003：实现裁剪 sheet、遮罩、四边与四角控制柄。
- UI-004：实现移动、悬停光标、键盘操作和“重置为居中”。
- UI-005：实现预设比例、自由比例和自定义比例输入。
- UI-006：实现代表图片切换与“应用到全部”说明。
- ENG-015：将显式裁剪与 exact 模式隐式居中裁剪接入处理流水线。
- TEST-003：覆盖横图、竖图、极端比例、不同方向和边界舍入。

周验收：混合横竖图批次可使用同一归一化位置输出，无越界、无比例漂移。

### 第 4 周：WebP、命名、目录与设置

目标：补齐五种格式和完整输出规则，设置可跨启动保存。

任务：

- ENG-016：正式接入 `libwebp` C wrapper 与 Swift `WebPEncoder`。
- ENG-017：实现 WebP 品质、alpha、ICC/EXIF/XMP mux 与 GPS 清除。
- ENG-018：实现命名模板解析、变量渲染、非法字符处理和即时示例。
- ENG-019：实现磁盘现有文件与批次内部的冲突避让。
- ENG-020：实现默认原目录、统一目录和目录写权限预检。
- ENG-021：实现 security-scoped bookmark 保存、恢复和失效重选。
- ENG-022：实现上次参数、品质、目录、命名模板和本机成功计数存储。
- UI-007：实现输出设置和 Settings 窗口。
- TEST-004：覆盖 WebP、命名冲突、权限与设置迁移测试。

周验收：五种格式全部可导出；重启后设置恢复；任何输出都不会覆盖已有文件。

### 第 5 周：批处理调度、进度、失败与取消

目标：把单图流水线升级为可控、可恢复的大批量任务。

任务：

- ENG-023：实现 actor 隔离的 `BatchCoordinator` 和 2–4 路有界并发。
- ENG-024：实现轻量进度快照、成功/失败计数与错误聚合。
- ENG-025：实现同目录临时文件和原子提交。
- ENG-026：实现持久化 `RunLedger`，记录临时文件和本轮新建输出。
- ENG-027：实现取消传播、停止调度、安全点和台账清理。
- ENG-028：实现异常退出后的未完成任务发现和可控清理。
- ENG-029：实现成功计数的批次最终提交语义。
- UI-008：实现进度页、取消确认、清理状态和完成/失败清单。
- TEST-005：注入编码失败、无权限、磁盘不足、取消和清理失败场景。

周验收：在不同阶段取消均不触碰原图和预先存在文件；失败项不会中断其余队列。

### 第 6 周：质量、双语与自用发布

目标：形成可签名分发的首版候选构建。

任务：

- QA-001：完成简体中文与英文翻译和长文本布局检查。
- QA-002：完成 VoiceOver、键盘导航、焦点、tooltip 和对比度检查。
- QA-003：执行 1,000 张图片压力测试和超大图片内存分析。
- QA-004：使用 Instruments 检查内存增长、主线程 I/O 和并发问题。
- QA-005：完成五种格式、元数据和取消清理的完整回归。
- REL-001：完善应用图标占位、版本号、许可证和隐私说明页面。
- REL-002：执行 Release Archive、签名、Hardened Runtime 和 notarization。
- REL-003：生成首版测试说明、已知问题和发布检查表。

周验收：所有 P0 用例通过，Release 构建可在另一台受支持 Mac 上安装运行。

### 第 7 周：风险缓冲

只用于解决下列问题，不在此阶段增加功能：

- WebP 双架构、签名或元数据兼容问题。
- App Sandbox 原目录授权差异。
- 大图内存峰值或取消清理竞态。
- 本地化、可访问性和发布构建阻断项。

若前六周没有消耗缓冲，则用于增加测试覆盖和性能优化，不扩大 MVP 范围。

## 5. 任务依赖与优先级

| 工作包 | 依赖 | 优先级 | 阻塞内容 |
|---|---|---:|---|
| SPIKE-01 WebP | 无 | P0 | WebP 正式接入、发布构建 |
| SPIKE-02 沙盒 | 无 | P0 | 原目录导出、目录设置 |
| SPIKE-03 元数据 | 无 | P0 | 全部编码器验收 |
| 导入队列 | 工程基线 | P0 | 所有批处理功能 |
| 尺寸流水线 | 核心模型、测试样本 | P0 | 裁剪、编码、任务调度 |
| 裁剪编辑器 | 尺寸流水线 | P0 | 统一裁剪验收 |
| WebP 编码 | SPIKE-01、像素流水线 | P0 | 五格式完成 |
| 目录与命名 | SPIKE-02、原生导出 | P0 | 安全批处理 |
| 任务台账与取消 | 输出提交规则 | P0 | 可发布版本 |
| 双语与可访问性 | UI 稳定 | P0 | MVP 完成 |
| 性能优化 | 批处理完整 | P1 | 大批量质量门槛 |

P0 是首版不可缺少项。P1 可以调整实现深度，但不得破坏大批量稳定性。

## 6. 每日开发规则

- 每个任务先写可测试的验收条件，再实现。
- 核心尺寸、裁剪、命名和台账逻辑不得直接写在 SwiftUI View 中。
- 任何文件写入功能必须同时提供“原图不变”和“不会覆盖”测试。
- 任何取消路径必须提供正常、失败和重复取消测试。
- 引入第三方代码前检查许可证、架构、签名和网络行为。
- 每个工作日结束前保持 Debug 构建和单元测试通过。
- 每周末生成一次可运行构建并按对应周验收标准演示。

## 7. 测试资产计划

在测试 target 中建立可重复的小型 fixture 集：

- 五种支持格式各至少 3 张：无元数据、带 EXIF/GPS/ICC、带旋转方向。
- 横图、竖图、方图、极宽和极高图片。
- 带 alpha 与不带 alpha 图片。
- 1 px 边界、小图、超大图和 WebP 尺寸上限样本。
- 损坏文件、扩展名与内容不一致文件。
- 同名、非法字符、超长名称测试项。

大型压力测试图片不提交到普通源码仓库；使用生成脚本或独立测试资产包，并记录校验值。

## 8. 风险与应对

| 风险 | 影响 | 预警信号 | 应对 |
|---|---|---|---|
| WebP 静态库无法顺利签名或双架构构建 | 阻塞格式承诺和发布 | Archive/link 失败 | 第 1 周前完成 SPIKE-01；保留源码构建方案 |
| 沙盒仅授权单文件而非父目录 | 默认原目录无法写入 | 同级临时文件创建失败 | 预检并请求父目录授权，不静默换目录 |
| metadata 跨格式映射不完整 | 隐私或色彩问题 | GPS 残留、色差、方向错误 | 建立 fixture 和自动 metadata 检查 |
| 大图并发导致内存峰值 | 崩溃或系统压力 | 内存随并发快速上升 | 缩略解码、有界并发、及时释放缓冲 |
| 取消与文件提交竞态 | 遗留输出或误删 | 清理台账与磁盘不一致 | 原子提交、持久台账、故障注入测试 |
| 命名预检后被外部程序占用 | 覆盖风险 | 最终 rename 冲突 | 执行时再次无覆盖校验并更新后缀 |
| 双语文本后期改布局 | 发布延迟 | 英文截断、VoiceOver 缺失 | 从第 1 周启用 String Catalog，第 6 周只做收敛 |

## 9. 变更控制

开发期间新需求按以下规则处理：

- 修复原图安全、隐私、数据丢失、崩溃和验收不一致：直接纳入 P0。
- 不改变用户流程的小型易用性修正：评估不超过半日可纳入当前周。
- 新格式、逐张处理、智能裁剪、历史、CLI、远程统计等：进入后续版本，不占用 MVP 缓冲。
- 任何影响格式、裁剪语义、默认目录或取消删除范围的变更，先更新产品与技术文档再编码。

## 10. MVP 完成定义

同时满足以下条件才视为首版完成：

- `docs/05-delivery-plan.md` 中 A–J 验收场景全部通过。
- JPEG、PNG、WebP、HEIC、TIFF 导入和导出矩阵通过。
- 原图安全、无覆盖、GPS 清除和取消清理测试通过。
- 1,000 张图片测试中 UI 可响应，内存不随已完成数量线性增长。
- 简体中文、英文、键盘和 VoiceOver 主流程可用。
- Release Archive、签名和 notarization 完成。
- 已知问题中不存在数据丢失、隐私、崩溃或主流程阻断项。
- 文档、许可证和发布说明与实际实现一致。

## 11. 开始实施时的第一批任务

建议按以下顺序立即执行：

1. SPIKE-01：WebP 最小编码与 Archive 验证。
2. SPIKE-02：沙盒原目录权限验证。
3. SPIKE-03：元数据 fixture 与 GPS 清除验证。
4. ENG-001/002：正式工程和测试基线。
5. ENG-003/007：先实现核心模型与纯尺寸算法。

前三项完成后重新核准一次 30 日估算；只有发现必须改变产品范围或第三方依赖策略时才暂停进入正式开发。
